# Product-dashboard conventions

The conventions the front follows when it authors **work-ledger content** — the work items
(carriers) on the product-dashboard. They are imported wherever the front creates or advances a
carrier: `raise` at create, `shape` (the shaping session) as it shapes, a dashboard `edit` at a terminal
disposition. They live here, as a vendored reference, so they hold the same way **regardless of which
node enacts them** — a dedicated curator skill, or the front nodes directly.

## The content/state write-boundary (the hard line)

The carrier (`work-item-schema`) splits by **who writes each field**. Content authoring writes the
**content half only**:

- **Author CONTENT** (the deliberate "why"): the problem/opportunity statement, `outcome_link` (the
  OKR it serves), `value_prop_link` (the VPC job/pain/gain), `risk_state` (the four-risks evidence
  state), `tier` (the per-item dial override), the solution summary (only once `committed`), `links`
  (spec / build PRs / experience-contract / debrief), `disposition` (for parked/killed), and the thin
  sprint-record beside the ledger.
- **Never write `current_stage`** — it is **projected** from the traversal (operator-overridable),
  derived, never authored (`work-item-schema`, `record-gate`).
- **Never advance `lifecycle_state`** — it advances **only at a gate** (operator go/no-go). Render an
  item under its current zone; never move it.
- **Never decide or append a `gate_decision` here** — `record-gate` (the single mechanical writer) is
  the sole appender; the decision is the operator's at each gate, the append is `record-gate`'s, never
  content's.

A request to advance a stage, pass a gate, or mark an item shipped/live is **surfaced as an
operator/gate action**, not performed. The boundary is **structural** (`work-item-schema`):
projection owns the stage, gates own the lifecycle — so it holds independently of any one writer.

## The two content invariants

- **Problem-framed until committed, and laddered to an outcome.** A work item carries a *problem /
  opportunity*, not a pre-committed feature, through the forward view; the solution summary is
  populated **only once committed**. Every `outcome_link` is an **authored** link to a real objective
  (never inferred), so the by-contribution rollup is trustworthy. An item that can only be stated as a
  feature, or that ladders to nothing, is not ready.
- **Nothing is destructively lost; the record is durable.** Killed and parked items are **retained
  with a `disposition`** (the anti-portfolio learning record); record content (problem, links,
  `risk_state`) is **kept once an item ships**. A work item is **never deleted**.

## Create, advance, graduate

- **`raise` creates** a carrier (a WI or a standalone IU) — the front's create action: identity +
  initial content, placed by content in the forward view, never by setting lifecycle (a gate does
  that) or stage (projected). `raise` writes the **carrier `.md` only** — it does **not** hand-write
  the manifest row: the manifest is a committed derived index, regenerated by the `refresh-manifest` build script (resolved via the harness binding — the
  same carrier-only discipline `triage` follows on the incremental create path).
- **`edit` advances** an existing carrier's content — including the **terminal disposition**: a WI
  `shape` (the shaping session) resolves as not worth an IU is parked / killed / deferred here, carrying its
  `disposition` (`work-item-schema`).
- **Graduate per the harness's git policy.** How a content change graduates — a labelled PR or a
  direct push — is **not hardcoded here**: resolve your repo/path against `@git-policy` (**no entry ⇒
  labelled PR**; the entry shape + most-specific-wins + fail-closed live in `git-policy-schema`, not
  restated here). When it resolves to **`pr-gated`**, graduate via a labelled PR: group content edits
  in one operator-decision frame into one PR; split across frames; **never bundle a structural ledger
  change with content edits** (`context-curator`); duplicate-check the open queue before opening; the
  PR description **is** the proposal — no separate file. When it resolves to **`direct`**, push the
  content change directly (no PR ceremony).

## Write-boundary guard

`lifecycle_state` and `gate_decisions` are written by the **single mechanical writer `record-gate`**
(`work-item-schema`) — no content edit and no other node touches either field. The guard is
mechanically enforced, not conventional: **the build gate rejects** (a) any edit of `lifecycle_state`
or `gate_decisions` that does not come from `record-gate`, **and** (b) any `gate_decisions` entry on a
**product gate id** carrying `decision_provenance: agent-auto` or recorded from an **unattended**
(dispatch-run) context — except the two carve-outs (the `agent-provisional` hold and the
ancestry-reconcile record; gate-model §decision-provenance). So the hard line above — never advance `lifecycle_state`, never append a
`gate_decision` — is enforced at build: a content author that touches either field fails the build,
and a product-gate decision can only be recorded operator-attested.

## The outstanding operator-actions "needs-you" surface

The dashboard renders a **"needs-you" list** of outstanding operator obligations — derived from the
`<sg-operator-action>` open/close lifecycle (the `<sg-*>` family, `sg-root-instructions`), not authored on a carrier. Because a
*close* about an obligation opened elsewhere can suppress an operator-facing item, the surface follows a
**fail-safe, attended-proposal discipline** (a forged or colliding event can only **add** a marker, never
**subtract** a real obligation):

- **Only an attended/attested open populates the needs-you list.** An open emitted from an **unattended**
  (dispatch-run) or non-authoritative context counts toward **friction metrics only** (an
  aggregate, never an item-by-item surface) — so forged-open spam cannot bury a real needs-you.
- **Only an attended/operator-attested close — or a `record-gate`-attested gate close — hides an item.**
  An **unattended, non-authoritative, or cross-harness** close cannot hide; it derives the item to
  **`close-proposed` (still visible, marked "someone proposed closing this")**, never to closed-and-hidden.
- **Honest under capture.** Under partial merge an unmatched open is **`possibly-outstanding (capture
  incomplete)`**, not a confident nag; it flips to closed (no phantom nag) when the missing log arrives.

This mirrors the `record-gate` authority on the durable side: the *durable decision* rides `record-gate`
(operator-attested); the *friction/outstanding view* rides `<sg-operator-action>` — a forged close adds a
visible marker, never silently clears a real obligation.
